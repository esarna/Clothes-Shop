# Staging Layer – Purpose and Justification

## 1. Purpose of the Staging Area (SA Layer)

The Staging Area (SA layer) is the first and only landing zone for raw
data extracted from source systems (CSV files). It acts as a controlled
buffer that sits between raw source files and the normalized BL_3NF layer.

Key purposes (ref: ETL courseware, ch. 1 – ETL Subsystems):

1. **Raw data preservation (ETL Subsystem 3 – Extract System)**
   Data is stored exactly as received from the source (1:1 mirror via
   `ext_` foreign tables), without any business transformations applied.

2. **Offline extraction support (ETL courseware ch. 3.2.2)**
   Source data arrives as flat files (CSV). The SA layer provides the
   correct physical extraction pattern: files → ext_ (file_fdw) → src_.

3. **Deduplication (ETL Subsystem 7)**
   Raw CSV files may contain physically duplicate rows. The SA layer
   (src_ tables) is the correct place to remove them before they pollute
   normalized structures. Cross-source deduplication (same customer in
   two systems) is handled subsequently in BL_3NF using the
   Hierarchy L1 approach (Deduplication.pptx, Slide 11-12).

4. **Data cleansing and type conversion (ETL Subsystem 4)**
   `src_` tables apply proper data types (DATE, DECIMAL, INTEGER),
   NULL handling, and defensive regex-based cast validation. Bogus
   values that cannot be cast are stored as NULL rather than causing
   load failures.

5. **Sensitive data filtering**
   SSN, credit card numbers, CVV, IBAN are present in `ext_` tables
   (raw mirror) but explicitly excluded from `src_` tables and all
   downstream layers (BL_3NF, BL_DM) per Business Template
   requirements ("Critically Sensitive fields excluded").

6. **Decoupling sources from DWH**
   If a source CSV changes its structure, only the SA layer needs
   updating. BL_3NF and BL_DM remain unaffected.

7. **Restartability (DWH Presentation requirement 3)**
   `TRUNCATE` before `INSERT` in the SA load scripts ensures the
   entire load is idempotent and restartable without side effects.

8. **Auditability**
   `TA_INSERT_DT` column in every `src_` table records when each row
   was loaded into the SA layer (Naming Conventions – TA_ prefix for
   technical attributes).

## 2. Why Data Cannot Be Loaded Directly Into the 3NF Layer

Loading data directly from CSV files into BL_3NF is technically
impossible and architecturally wrong for the following reasons:

### 2.1 Normalization requires decomposition
A single CSV row contains data for multiple 3NF tables simultaneously:
product, customer, employee, store, payment type, and the fact record.
These must be split in a controlled, ordered ETL process.
Direct loading would violate 3NF atomicity.

### 2.2 Surrogate key generation (ETL Subsystem 10)
Every BL_3NF table requires surrogate keys generated by dedicated
PostgreSQL sequences (e.g. `SEQ_CE_CUSTOMERS`, `SEQ_CE_PRODUCTS`).
These do not exist in CSV files. They are generated during ETL.

### 2.3 SCD2 logic (ETL Subsystem 9 – SCD Manager)
`CE_CUSTOMERS_SCD` and `CE_PRODUCTS_SCD` implement Slowly Changing
Dimension Type 2. This requires comparing each incoming row against
the existing table to decide: INSERT a new version or close the
current one (set END_DT, IS_ACTIVE = 'N'). This is a multi-step
procedural operation that cannot be expressed as a single bulk load.

### 2.4 Cross-source deduplication (ETL Subsystem 7)
The same customer or employee may exist in both sa_retail and sa_ecom
with different IDs (customer_id vs user_id). The Hierarchy L1 approach
(Deduplication.pptx) resolves this at BL_3NF level, not at CSV load time.

### 2.5 Source triplet population
Columns `SOURCE_SYSTEM`, `SOURCE_ENTITY`, `<name>_SRC_ID` (Naming
Conventions – source triplet) must be populated with correct metadata
values during ETL. They do not exist in the CSV.

### 2.6 Default values / NULL replacement
Missing attributes must be replaced with 'N/A', -1, or 'NOT-CAPTURED'
defaults (e.g. retail has no customer email, ecom has no store_code).
This transformation requires knowledge of the target schema,
which is not available at raw extraction time.

### 2.7 Default rows (-1)
Every BL_3NF and BL_DM table requires a mandatory default row with
surrogate key = -1 and all text columns = 'N/A'. This is a DWH-layer
concern, not a source-layer concern.

**Conclusion:**
The Staging Layer is an architecturally mandatory intermediate zone.
It guarantees clean, deduplicated, typed, and auditable data is
available for the BL_3NF ETL pipeline, while keeping raw data
safely preserved in `ext_` tables for reprocessing if needed.
